Summary and more details below
We built an unattended multi-game path: run_headless.py + HeadlessGameRunner + GameManager, which can run more games after each other in one batch. With NO_GUI_AT_ALL_TF=True and four AI seats, batches write per-game result.json and batch_summary.json (wins, stuck/error, dice, give-up/salvage dig fields, etc.).

Initially the performance (=time to run) such a batch was pretty long. Therefore we spend quite some time and effort performance improvement.  Runtime improved from roughly ~1–2 min/game toward ~30 s/game on recent product-scale runs (perf work on Strategy-Engine / L2 policy paths).

After running a batch, which played multiple games, we should assess each individual game regarding and check if the Strategy-Engine did what it is supposed to do. However we don't have the time to do so, which is what a CS-probe is made (CS =  Change Strategy). The CS-probe looks for changes in Victory-Ways and changes in sticky target withing a selected Victory-Way. If such cases are detected, these are reported, so we can spend time assessing the most interesting individual games to check if the Strategy-Engine is doing what it is supposed to do. We used digs to tune when to re-plan (setbacks, product sticky/explicit-recalc policy) rather than relying only on manual full-game review. We optimized the L2 reset for each AI Player, after ETA setback and after 4 own turns (default: [2,[4,4]]). This means we actively check once again the best strategy, given the current circumstances (both Victory-Way and sticky target), every 4 own turns. 

We made a LA/LR probe as well. This probe looks for game situations where the selected game strategy to keep pursuing LA and/or LR should be abondonned because it is quite clear that an opponent is unstoppable in achieving and pertaining LA and/or LR. Again these game situations are reported so that we can spend time assessing those interesting games to check if the Strategy-Engine is doing what it is supposed to do. Based on multiple smoke tests we defined theta (θ) and optimised this for LA and LR seperately. Theta (θ) is the give-up threshold for LA or LR: “how hopeless does the race look before we abandon that special (LA/LR)?”

After focussing on pillar A (gods_view), one other thing came to mind and that is that there might be situations where none of the 142 Victory_Ways is feasible anymore. In such cases the objective should be to gain as much victory points asap, ignoring the component that can never be achieved. If LR can't be achieved: 1) Find a viable Victory-Way not having  LR as component, 2) If no such Victory-Way is feasible, find a Victory-Way, ignore LR and find the Victory-Way where a) it is feaible to achieve the remaining components AND b) still least number of own turn is needed to do so. All this is implemented as "Give-up escape + partial Victory-Way salvage". The core fix here is that after give-up, the Strategy-Engine must not re-lock a dead special (LA/LR) forever. Escape (specials-dead episode, portfolio filter, force-adopt, sticky gates) plus partial salvage: 1) Prefer Victory-Ways that never needed the dead components (T1), 2) If none, strip dead components and rank residual need by least own-turns (T2) and 3) Sticky carries partial_plan / ignored_components (S4); expansion death is geometry-fair (S5/S5b); digs record adopts and switch quality (S7/S7a, G6). Needed implementations: S0-S7 + D0-D7 + G0-G6. Note: S8 (VP scrape when T1/T2 empty) waits for digs showing the need to implement.

## Challenges (where the line of reasoning is incomplete or risky)

### 1) `dice_roll_history` is not the sequence you think

In Gen3 today:

| Attribute | What it is |
|-----------|------------|
| **`game.dice_rolls`** | List of **(d1, d2)** rolls — the **sequence** |
| **`game.dice_roll_history`** | Length-13 **histogram** of totals 0–12 (counts), **not** order |

Saved games already serialize both. So “wire dice history for replay” is mostly: **treat `dice_rolls` as the source of truth**, optionally rename/document, not invent a new list from scratch.

**Replay needs the ordered list (or a scripted file via `DICEROLL_SET_TF` / `NAME_DR_FILE`), not the histogram.**

---

### 2) `game.seed` alone does not freeze a Catan game

A single `game.seed` is necessary but **far from sufficient** for “same 100 games twice”:

| Source of randomness | Seeded by `game.seed` today? |
|----------------------|------------------------------|
| Dice | Only if you **script** dice or seed the RNG that rolls them |
| TwP near-tie RNG | Partially (Stage D uses `game_seed` / `seed` when present) |
| Steal / robber target among ties | Often local `random` |
| DCard draw order | Deck shuffle at start / reshuffles |
| Hand-risk Stage D | Seeded when context has seed |
| Any other `random.*` | Easy to miss |

So: **seed is good plumbing; fixed dice sequence (+ fixed board + fixed deck if needed) is what actually matches games.**  
Best lab stack:

1. Fixed playboard (you already do),  
2. **Recorded `dice_rolls` sequence** (or pre-generated file) replayed with `DICEROLL_SET_TF`,  
3. Optional master seed for residual RNG,  
4. Log seed + dice path hash on `result.json`.

Without (2), “same 100 games” will **diverge after the first policy difference** even with the same seed, because different actions → different who-gets-robbed / different branches — and also because unseeded RNG still fires.

---

### 3) “Play the same 100 games twice” breaks after the first divergent action

Even with **identical dice**:

- P2 with 3a/3b builds differently → different board → later **legal** options differ.  
- Opponents still use sticky → they react to P2’s different board.  
- You are **not** replaying the same *game tree*; you are replaying the same **chance inputs** under two P2 policies.

That is still a valid experiment, but rename it mentally:

> **Same dice + board + IP, different P2 reassess policy**  
> not “the same game played twice.”

For causal claims, that is actually what you want. Just don’t expect identical round counts or identical P1/P3/P4 lines.

---

### 4) 3a (L2 on +1 VP) and 3b (L2 every own turn) are not pure “reassess Victory-Way” knobs

**L2 ≠ switch way.** You already saw: L2 runs and **still keeps the same way**.  

So:

| Policy | What it actually does | Risk |
|--------|------------------------|------|
| **3b L2 every own turn** | Full portfolio + EH often; **may still refuse to switch** if switch needs ETA gain ≥ 1.0 and sticky hard-holds | Expensive; may measure **compute**, not **openness to new ways** |
| **3a L2 on VP gain** | Fires after own settle/city (and maybe LA/LR VP) | Sparse; misses “I’m stuck for 8 rounds on a dead way” |

If sticky **forbids** switch unless hard-invalid / big ETA gain, then 3a/3b can still yield **~0 way switches** and you’ll falsely conclude “reassess doesn’t help.”

**You must also loosen or instrument the switch gate for the treatment seat**, e.g.:

- Allow way switch on treatment seat with lower `STRATEGY_SWITCH_MIN_ETA_GAIN`, or  
- Force a **true multi-way compare** and log “best alt vs locked” even if you don’t switch, or  
- Explicit policy: “on 3a/3b, unlock sticky way and re-pick from top K.”

Otherwise the experiment confounds **“how often we L2”** with **“whether we may change way.”**

---

### 5) VP-gain trigger (3a) is a biased sample of “good” moments

Gaining a VP usually means **the current plan just worked** (settled/citied). Re-assessing then:

- Often **reinforces** the current way (confirmation),  
- Rarely catches “wrong way, grinding.”

The times you most need re-assess are often:

- ETA rising repeatedly (`estimator_jump` / setbacks),  
- target thrash / blocked,  
- specials lost,  
- many rounds without VP.

So 3a is a weak probe of **initial way quality under failure**. Better companions:

- **3c:** L2 when cumulative setbacks or ΔETA ≥ X,  
- **3d:** L2 when sticky target hard-invalid,  
- **3e:** scheduled L2 every N own turns (cheaper than every turn),  
- **3f:** L2 at fixed milestones (after 2nd settle, after first city, at 6 VP, at 8 VP).

I’d keep 3a as optional, not primary.

---

### 6) Every-own-turn L2 (3b) is heavy and may not answer “first way quality”

Order of magnitude: ~25 rounds × 1 L2 for P2 ≈ **25 L2s/game for one seat** (plus existing L2s). At ~80–130 ms/step overall, pure L2 is a big fraction of turn cost → P2 games slower, batch wall time up, and you mix **speed** with **policy**.

Also: if everyone else is sticky and P2 re-plans every turn, you measure **asymmetric multi-agent dynamics**, not pure “was first way good?”

Stronger design for **first-way quality**:

- **Arm A:** sticky as now (control).  
- **Arm B:** same dice; P2 may **re-open way only at few gates** (e.g. after each own structure, or every 3 own turns), with **switch allowed**.  
- Log for P2 at each L2: `locked_way`, `best_alt_way`, `eta_locked`, `eta_alt`, `switched?`.

That separates:

- **Information:** “L2 saw a better way”  
- **Action:** “we switched”  
- **Outcome:** win/VP  

---

### 7) Only treating P2 interacts badly with “P2 is the weak seat”

Your 100-game IP2 batch: **P2 ~10% wins**. If you only empower P2:

- Positive result: “reassess helps the weak seat” (great).  
- Null result: may mean **IP seat/map**, not sticky (P2’s two settles are just bad).  
- You learn less about **first-way quality for a strong seat**.

Better: run the same dice library with treatment on **P1, P2, P3, P4 in separate arms** (or rotate which seat gets 3x), or treat **all seats** with a cheap reassess policy in one arm.  
Starting with P2 is fine as a pilot, but don’t over-generalize.

---

### 8) “Quality of initial way” needs fit metrics, not only win rate

Even a perfect reassess policy might not move win rate much if:

- IP already determined fate,  
- way switches are rare because **no better way exists**,  
- opponents punish expansion.

Pair the experiment with the **first-way fit** idea (own pips, board pips, d≈2 portfolio). Then:

| Pattern | Interpretation |
|---------|----------------|
| Low fit + reassess → more switches + better VP | Sticky was wrong; reassess helps |
| Low fit + reassess → switches but no better outcome | Board/IP doomed |
| High fit + reassess → no switch | Sticky was right |
| High fit + reassess → switch + worse | Switch gate / L2 noise thrash |

Without fit scores, win rate alone is underpowered and confounded.

---

### 9) Sample size and power

100 games with ~10–33% win rates: moving P2 from 10% → 15% is only **+5 wins** — noisy.  
For a clear seat effect you may want **200–500 matched dice seeds**, or primary metrics **mean VP / mean rank**, not only win rate.
